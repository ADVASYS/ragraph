# Internationalization

RAGraph ships with **four complete locales**: German (`de`), English (`en`), French (`fr`) and Spanish (`es`). Every user-visible string in the UI passes through `i18next`, and the RAG agent answers in the user's language by default.

## File layout

```text
src/i18n/
├── index.ts              # i18next configuration and initialization
└── locales/
    ├── de.json
    ├── en.json
    ├── es.json
    └── fr.json
```

Keys are nested by feature / domain, e.g.:

```jsonc
{
  "settings": {
    "provider": {
      "baseUrl": "Base URL",
      "apiKey": "API key"
    }
  },
  "chat": {
    "composer": { "placeholder": "Ask anything…" }
  }
}
```

Keep keys alphabetical within their namespace — it makes diffs readable and keeps contributors from stacking new keys at the bottom.

## Runtime configuration

`src/i18n/index.ts` wires `i18next` with:

- `react-i18next` integration.
- `i18next-browser-languagedetector` using `localStorage` and browser language, in that order.
- `fallbackLng: 'en'`, `supportedLngs: ['en', 'de', 'fr', 'es']`, `load: 'languageOnly'`.
- `returnNull: false` so missing keys render as the key string during development (surfaces gaps immediately).
- `interpolation.escapeValue: false` because React already escapes.

The active language is mirrored to `AppSettings.language`, which is applied on startup in `src/app/App.tsx` via `i18n.changeLanguage(settings.language)`.

## Adding a key

1. Add the key to **every** file under `src/i18n/locales/` — no partial translations. If you do not speak a language, copy the English value and mark the PR for a follow-up review.
2. Use it in the component:
   ```tsx
   const { t } = useTranslation();
   return <Button>{t("settings.provider.save")}</Button>;
   ```
3. Interpolate values as usual:
   ```tsx
   t("chat.sourceCount", { count: sources.length });
   ```
   Pluralization uses i18next's `_one` / `_other` suffix convention:
   ```jsonc
   {
     "chat": {
       "sourceCount_one": "{{count}} source",
       "sourceCount_other": "{{count}} sources"
     }
   }
   ```
4. Keep the keys alphabetical within the namespace.
5. Avoid one-off strings in the code; prefer a descriptive key even for one-liners so the string can be re-used and reviewed in context.

## Backend-side language handling

The RAG agent's system prompt includes the current language code so answers are produced in the user's language unless the user writes in another language. The analyzer detects the document language during ingestion and stores it on the `Document` node (`props.language`), which lets the agent translate or summarize across languages without losing the original.

## Review checklist

Before merging i18n work, verify:

- [ ] Every new key exists in `de.json`, `en.json`, `es.json`, `fr.json`.
- [ ] No hardcoded English strings were left behind in JSX.
- [ ] Plural forms use `_one` / `_other` where counts are involved.
- [ ] Keys are alphabetical within their namespace.
- [ ] The UI still fits in all four languages (German tends to overflow buttons — shorten the English master when it does).
